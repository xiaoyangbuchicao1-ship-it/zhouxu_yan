# 工程失误与后续约束

更新：2026-11-20。用户要求持续保留本次失误，作为后续修改前的项目记忆。

这份记录约束本项目的实施和验收，不覆盖用户之后的明确要求。

## 管理台与长连接补充（2026-11-22）

- 首屏读取失败不能展示默认 0 或空列表；数据尚未取得与真实没有数据必须区分。修改请求成功后以服务端回执确认结果，后续刷新失败单独说明，不把成功的修改误报成失败，也不自动重发。
- 账户停用、退出或登录过期后，已打开的事件流也必须重新检查访问权并结束连接。事件只从当前授权会话的任务集合中输出；不能把共享 EventHub 的全部事件直接传给未指定 run_id 的连接。断开访问不等于取消后台任务，两者分开处理。
- 高频事件复查使用现有鉴权的只读路径，不缓存撤权状态，也不为每段文字更新 last_seen_at 和提交 SQLite。
- Radix 弹窗与菜单渲染到 Portal 后不会继承页面的局部变量；独立声明必要设计变量。自定义组件样式还需有明确作用域，防止与 Tailwind 工具类同优先级而被构建顺序覆盖。真实截图发现过标签栏灰底居中，不能仅凭 DOM 和功能检查宣称视觉验收完成。

## 新增长期约定：全新构建、镜像源与删除决策（2026-11-21）

- 依赖缓存和旧代码要分开判断。`pyproject/uv.lock/package-lock`、系统包版本和基础镜像 digest 没变时，可以复用已下载的依赖层；这不等于复用旧源码、旧配置、旧数据库或旧运行数据。正式构建必须把当前源码和配置重新复制进镜像，并核对依赖合同后再决定是否需要 `--no-cache`。
- 网络下载失败先尝试项目配置的镜像站或备用镜像源，并区分“下载源失败”和“代码/依赖解析失败”。多次镜像源仍失败时停止，不擅自改成缓存构建；必须把可选方案交给用户决定。
- 清理失败构建产生的临时容器、日志和本任务临时目录可以直接做；删除 SQLite、运行历史、用户文件、迁移备份，或选择不做备份属于不可逆决策，必须先向用户询问并说明后果。

## 最新模型开放与维护约定（2026-11-21）

- 用户已取消逐型号工具/流式/续接验证上架门槛。聊天可用模型共用工作模式清单，工具权限属于统一执行层。验证记录仍按真实结果保存，不再用记录是否存在决定是否发送工具；不要恢复旧的前端、API、绑定或协议开关。
- 遇到旧依赖阻断先核对实际解释器、安装版本、项目声明与锁文件；仍在使用的按锁定版本修正，确认不用的旧代码和配置删除。本次本机 `argon2-cffi 21.3.0` 升至已锁定的 `25.1.0` 后，原健康测试通过，不需要业务兼容补丁。
- 浏览器验收按实际合同断言：具体工具权限可能在任务受理后、执行前拒绝；公开错误只含用户文案，诊断码通过授权诊断入口核对。Markdown 正文不能直接与渲染后的纯文本全串比较，Windows 剪贴板换行按平台规范归一后比对。

## 1. 不根据沙箱的进程视图断言 Docker 没启动

本次 `docker info` 在沙箱中返回 named pipe 的 permission denied；沙箱中看不到 Docker 进程。获准的宿主机诊断则确认 Linux Engine 正常。

以后区分 CLI、引擎、沙箱访问权限和应用启动四层。只有实际证据才能断言某层故障。需要宿主机诊断时明确申请权限，不更换工具绕开已拒绝的操作，不修改 pipe ACL 或全局系统设置。

## 2. 改状态必须迁移所有现存持久化位置

本次只处理旧 JSON，漏掉了已经存入 SQLite 的旧值。API 在恢复历史会话时因 completed 不属于新 RunStatus 而退出。会话历史投影还保存着 completed 和 stopped。

以后检查 RunStore 快照、嵌套 Run 事件及 conversation_runs 投影；提供只读预检、明确执行命令和成对 SQLite 备份。只映射 Run 生命周期字段，不替换业务步骤状态或正文中的同名词。迁移后对照备份确认正文、执行状态、事件序号、文件记录未丢失。应用启动不做隐式旧数据兼容。

当前映射：completed → succeeded，interrupted → paused，stopped → cancelled。TaskStepStatus 的 completed 原样保留。

## 3. 公开版本号不能充当输入是否被替代的判断

暂停和节点进度都会增加 revision。原执行器把 revision 变化视为输入已被更新，导致普通模型任务一直保持 pausing。

以后用实际控制意图区分暂停、取消和输入更新；三种行为覆盖普通模型和图任务。检查暂停请求被保存后进程重启的情况：恢复为 paused，等待用户继续。耗时按原累计值加本次执行只结算一次。

## 4. 内部合同测试不能代替用户端到端验收

本次直接调用 scheduler 的脚本没有经过登录、HTTP、前端、真实模型和下载路径，不能据此宣称真实用户任务已通过。

以后每阶段保留 3～5 条核心用户旅程，按实际范围验证入口、状态、恢复和可见结果。阶段性静态检查、合同测试、模拟执行和真实模型测试分开报告。未运行的项写明未运行。

## 5. 不能把演示摘要登记成真实节点成功

本次 descriptor_node 只根据 config.summary 生成摘要和引用，并未读取 Skill、调用工具/模型或登记真实文件。它只能说明图合同可以表达这些节点，不能证明节点已经执行。

以后生产节点必须接通现有 SkillRegistry/read_skill、RegisteredAction、模型端口和文件工作区。结果引用必须对应实际读取或生成的内容，文件必须存在、哈希匹配并能授权下载。未接通的节点明确失败，不返回“已完成”。演示处理器只用于明确标记的合同测试，不进入生产默认路由。

## 6. 用唯一受支持的部署环境验证

Windows asyncio 创建事件循环被沙箱 socket 权限阻断，npm 也曾被 Windows 文件锁阻断。继续修改业务实现并不能排除这些环境限制。

以后真实运行与依赖构建使用批准的 Docker Linux Compose。Windows 启动器先检验 Linux Engine 和 Compose，再读取部署配置。不要因环境错误改 package-lock、事件循环策略或引入另一套原生部署路线。

## 7. 端口与服务身份以实际部署为准

本机舟序发布到 127.0.0.1:18080；8080 已有其他服务。初次硬编码 8080 导致误测到其他站点的 404。

以后先用 docker port/Compose 状态确认实际发布地址，再验证舟序入口与 API。不要根据 README 的默认端口断言当前配置。

## 8. 终态任务也必须从服务端恢复节点与耗时

本次实时卡能显示节点，但刷新已完成任务后，历史消息既没有接入 Run 快照的节点与耗时，也没有渲染时间线。只测运行中的页面会漏掉这个错误。

以后通过同一个 run_id 把服务端快照关联到历史消息，实时和历史回答复用时间线组件。不靠永久保留实时卡维持显示，不新造一份前端持久状态。必须验收任务完成后刷新、重新打开会话以及暂停后刷新；完成节点的状态、尝试次数、输出引用和累计耗时都要保留。

## 9. 容器已启动不等于入口已就绪

本次单独更新 API 后，`up -d --no-deps` 返回成功，但立刻测试 Web 收到 502；API 健康检查通过后，同一代理恢复 200。没有证据表明 DNS 或模型故障，不为这个启动窗口修改代理配置。

以后更新后先等待服务健康（例如 Compose 的 `--wait`），再经过实际 Web 端口确认 `/api/healthz` 为 200，之后开始用户测试。启动中的 502 必须与持续故障区分，未就绪的运行不计为通过。

## 10. 暂停请求的过渡态不能当成生成态

暂停接口先返回 `pausing`，后台在最近一个检查点保存完成后才变成 `paused`。前端若把 `pausing` 当成 `running`，会继续显示旋转加载、允许用户叠加补充输入，并在中止事件流后永远等不到最终暂停状态。

以后把 `pausing` 作为独立的可见状态：显示“暂停中”与保存检查点提示，暂停期间不允许提交新输入；暂停请求返回后保留同一 Run 的观察，直到服务端明确返回 `paused`。真实验收必须检查“点击暂停后的即时画面”和最终状态，不能只轮询最终数据库状态。

## 11. 暂停后的补充要求必须恢复原 Run

本次发现：暂停后用户在输入框补充“先暂停后再继续”，前端把它作为普通新消息提交，创建了一个只有补充句的新 Run。真实模型因此把“暂停”当成新任务要求，进入 `waiting_user` 或 `task_blocked`，原任务上下文和检查点没有成为该次执行的明确合同。

以后暂停或可继续失败状态下的补充输入必须调用同一 Run 的 Continue 命令；原始 `RunInput.text` 不得被替换。补充内容单独写入持久化检查点，由运行层作为必选上下文传给模型，并明确“继续动作已接受、补充要求附着原目标”。前端应显示这一语义，刷新后仍显示补充要求。只有用户明确选择“重新做”或新建对话时才创建新 Run。

这条路径必须用真实浏览器和真实模型验收：检查 Continue URL、Run ID 不变、原目标不变、引导持久化、刷新后仍可见，并确认模型完成原任务。

## 12. 临时浏览器依赖不能成为验收入口

图任务验收脚本曾引用已删除的临时 `browser/node_modules`，在进入应用前就报模块缺失，造成测试基础设施误报。

以后过程脚本统一引用受支持的 Playwright 运行时或在脚本自己的临时目录显式安装锁定依赖；测试记录必须区分“测试入口失败”和“产品运行失败”，不能把前者归因于 API 或模型。

## 13. Linux API 的 SQLite WAL 不跨 Windows 文件系统打开

历史会话详情返回 200，但同一会话 snapshot 返回 500；堆栈停在 `SQLiteRunStore.visible()` 的 `sqlite3.OperationalError: unable to open database file`。运行库在 Windows bind mount，Linux API 持有 WAL 长连接；Windows 侧也曾打开该库。故障时 WAL/SHM 已不在目录，停止 API 后同一原库可读且完整性检查通过。共享目录与跨系统访问是已确认的风险边界；现有证据无法精确还原哪一次操作移除了 sidecar。

以后运行库放 Linux 数据卷，同一环境管理 WAL/共享内存；Windows 不打开在线运行库。迁移显式停服，源文件保留，通过 SQLite Backup API、完整性与逻辑哈希校验导入，空卷遇到旧库必须报错，不隐式创建空历史。保留原件与停止时点的配套业务库/文件；跨电脑先导出数据卷，不能复制已不再更新的旧 `data/runtime/`。禁止 `down -v` 当作普通重启。

同时修复健康检查的假正常：`/healthz` 必须实际读取运行库，SQLite 读失败返回 503。端到端验证需覆盖生成回答、刷新、服务重启再读取历史，不能仅检查容器是 running。

## 第一步补充约束（2026-11-20 本轮实测）

- 模式提升必须有结构化选择，普通文字不能当授权；别名入口复用同一校验。模型需要可发现的“申请工作模式”控制动作，不能靠关键词列举判断任务权限。
- 上传、界面资料更新与 Continue/确认按钮必须共享忙碌状态。测试要延迟真实上传并立刻尝试继续；只测“等上传成功后再点击”会漏掉竞态。
- 重复检索的停止条件不能撤掉交付需要的写入、编辑和编译能力；必须用实际工具列表回归验证。
- 摘要截断/失败时只能标注完整原文引用，不能伪装成成功摘要。正常摘要要遵守输出预算；清单由程序保存，别让模型复述上百个记录 ID 耗尽预算。报告分清真实长任务恢复和独立模型回放。
- 追加文件必须覆盖“替换文件成功、回执未完成”的中断窗口，而不只测回执已完成后的再次调用。未知副作用不自动重放。
- 可下载的 PDF/DOCX 与投稿级稿件是不同验收项。物理页号不等于期刊印刷页；篇幅、新法时态与引用元数据仍需分别校验。当前样稿存在这些质量限制，不能宣称全面达标。
