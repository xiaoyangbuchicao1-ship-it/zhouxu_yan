## 一、法律法条库：先分清文献、条文和版本

查法条时，用户往往会问“哪部法的第几条”“这条现在还有效吗”。因此，只有一堆能打开的文件还不够：同名法规可能有不同修订版本，同一个条号在修订后也可能对应不同内容。

法规库的整理围绕这条线展开：

```text
PDF、Word、HTML 原文件
  → 登记目录、归档原件、提取正文，再按条文整理
  → 转成文献记录和条文记录，保留分类、来源与版本关系
  → 保存可阅读的正文，切成较短的检索片段
  → 给片段生成相似搜索需要的向量
  → 检查文件、片段和向量是否一一对应
  → 导入搜索索引，验证后供网站查询
```

### 1. 起点：先把原文件收好，认清它们属于哪份文献

法规最初的独立工作区把材料分成四层，先让人能核对清楚，再交给程序转换：

| 原始目录 | 做什么 | 为什么需要这一层 |
|---|---|---|
| `01_目录与说明` | 登记文献、文件载体、条文索引、效力依据和整理变更 | 先有一份总账，知道收到哪些文献、做过哪些处理 |
| `02_原文档案` | 保存 PDF、DOCX、DOC、HTML 等原文件 | 后续提取出错时，有原件可以回查 |
| `03_可检索正文` | 保存从原文件提取的完整文字及提取状态 | 让整份文献可阅读，也能区分提取成功、待复核和失败 |
| `04_条文库` | 按条文保存正文、条号、章节和所属文献 | 把整份法规细化为用户实际要查的条文 |

这四层通过文献编号、载体编号及路径关联。同一份文献可能同时有 PDF 和 Word，因此不能把“文件有多少份”直接当成“法规有多少部”。正式语料包再把原始载体按文献编号归档到 `opensearch/corpus/originals/`。

每份文件都有保存位置和内容校验值。项目使用 SHA-256 计算校验值，可以把它理解为文件的“内容指纹”：检查时能发现文件是否改变、是否拿错。它能核对文件内容，不能证明文件本身就是官方现行文本。

这一步先完成，后面提取出的正文和条文才有明确的出处。

### 2. 把文献整理成两层：整篇记录与条文记录

转换脚本读取上述目录和索引，把“原件到完整正文”的来源关系，与“完整正文中的条文”分别写成两类记录：

| 层次 | 保存什么 | 解决什么问题 |
|---|---|---|
| 文献层 | 整份来源文献的名称、正文、分类、日期、原文件位置等 | 能知道这段话来自哪份文献，并回看较完整的内容 |
| 条文层 | 条号、章节、条文正文及所属文献 | 能查到具体条文，不必每次翻整份文件 |

整理后的正文另存为 TXT，结构化记录存为 JSONL。JSONL 就是一行一条记录的文本文件：每行把正文、名称、条号、来源等信息放在一起，程序可以逐条处理。少数历史条文记录包含多个条号，因此“条文记录数”也不能直接理解为独立法条数。

这一步只做结构转换与来源核对，尚未切检索片段，也没有计算向量。提取状态继续保留，不能因为记录已经转成 JSONL，就把待复核文字当成已核对正确。

目录里的分类可以帮助浏览，但一条记录的身份由稳定编号确定。换一个分类目录或换一台电脑，不应让它变成另一条资料；正式路径也使用相对路径，避免依赖某台电脑的盘符。

版本信息与正文一起保留。现有记录区分现行、已被替代、修改决定，以及关系尚未确定等情况。能确定关联时才指向对应文献或条文；没有充分依据时留作未解决，不能因为两版都叫“第三十一条”就认定它们内容相同。

这些关系反映本批资料的版本整理结果；后续法规修订，还需要核对并更新记录。

### 3. 为什么有完整条文，还要再切成片段

整篇法规适合阅读，短片段更便于搜索定位。用户只问一个义务或例外时，搜索系统需要先找到相关段落，再按所属条文补足上下文。

法规清单把检索分块上限设为 500 个字符。详细分块记录保留片段顺序、起止字符位置和切分原因；统一导入文件则保留检索所需字段，以及回到条文正文的路径。

送去计算向量的文字，还会加上法规名称、章节和条号，帮助搜索理解片段的背景。否则，多部法规里类似的“应当提交有关材料”，脱离名称和章节后很难区分用途。

这里形成了三个用途不同的东西：原文件留作依据，整理正文供阅读和核对，检索片段帮助快速找到相关位置。切成片段后，完整正文仍然保留。

### 4. 给片段建立两种查找方式，再核对是否装对

第一种按字词找，例如法规名称、条号或“船舶污染”。第二种按意思相近找，例如用户问“货物损坏由谁承担”，即使原文用词不同，也有机会找到相关内容。

第二种使用 BGE-M3，把文字转换成一组 1024 个数字，称为向量。数字用于比较相似程度，实际阅读和引用仍依赖正文。片段的向量输入、向量所在行、编号和内容校验值都有对应记录，避免把甲条文的文字配上乙条文的向量。

导入前检查本地资料，导入后再从搜索系统读回来核对。数量一致只是其中一项，还要检查正文、编号、路径、向量及版本字段是否相符。

### 5. 最后怎样供网站使用

验证通过后，程序通过固定的读取入口查询法规索引。索引可以理解为资料的“搜索目录”：它保存搜索需要的文字、字段和向量，找到命中后还能按记录回到正文。

当前法规物理索引是 `maritime_law_chunks_v2`，读取入口是 `maritime_law_chunks_read`。这里的读取入口是一个固定名称，发布时可以把它指向经过检查的新索引，网站不用跟着更改所有查询地址。

现有清单保存 69,221 条分块前的条文记录、2,375 条文献记录，形成 93,858 个检索片段；原始文件共有 2,379 份。这些数字分别在数记录、片段和文件，含义不同。

**这一库可以用起来的依据：**能搜到相关条文，名称、条号、版本与保存的资料一致，并能回看对应正文。是否适用于某个具体案件，还需要结合事实和时间判断。

## 二、案例库：先确保片段确实来自这份案件材料

案例的关键是把一份材料的身份、全文和片段接起来。搜索命中一段法院说理后，应能继续读取同一案件的前后内容，不能接到另一案，也不能把材料中的作者评析当成法院认定。

```text
Word 案例正文与摘要
  → 按案件编号配对，保留全文和原文件位置
  → 提取材料中已有的结构信息，连续切分正文
  → 用 BGE-M3 生成正式向量，形成案例交付包
  → 统一字段，给每案和每个片段建立对应关系
  → 核对片段在全文中的位置，以及正文覆盖情况
  → 核对已有向量，不重复计算相同资料
  → 形成完整的数据快照
  → 导入独立案例索引，供搜索和原文读取
```

### 1. 起点：先把 Word 正文与摘要配成同一案

案例库的上游原料保存在独立的案例工作区，主要是分目录存放的 Word 正文和摘要。整理脚本使用成熟的 `python-docx` 读取段落和表格，把文字提取出来，同时保留原文件的相对路径。

正文与摘要通过文件名中的 `HH` 案件编号配对。正文提供完整材料，摘要提供已有的标题、关键词和案情概述；摘要中的概述不能替代全文。缺摘要的案件仍保留正文，并记录缺项。

这里实际遇到过一个重号问题：`HH0583` 对应两份不同正文。整理时保留两份材料，把第二份稳定登记为 `HH0583-2`，并分别保存原路径。否则，简单地按编号覆盖文件，就会少掉一案。

接下来，脚本从材料中明确的栏目提取事实、争议、法院理由和裁判结果等内容，并按段落、句子及长度连续切分全文。完整案件与片段分别写成 JSONL，再配上正式向量及逐行说明，形成交付包。网站项目接收到的就是这一层资料，其中已经有“案例编号”“原文全文”和“片段编号”等字段。

原 Word 怎样整理成这份包，现在有文件和脚本可以核对；这些 Word 最初从哪些网站采集而来，本文仍没有完整依据。

### 2. 先统一字段，再核对片段是否真的属于这份全文

整理脚本把中文字段转成程序使用的统一名称，并保留案件全文。随后，对每个片段检查三件事：它标的是哪一案、它的文字能否在该案全文中找到、它从全文的哪里开始到哪里结束。

例如，一段文字即使很像某案的裁判理由，只要不能在对应全文中找到，就不能当成这份材料的原文片段入库。标题相似不能替代正文核对。

脚本还检查全文中非空白文字是否被分块覆盖。这样能发现“表面上案件已经入库，实际只入了一半正文”的问题。同一段文字若在全文里出现多次，会记录这些位置，不因文字重复就误认为原文缺了一段。

### 3. 法院、案号和日期怎样处理

早期整理提取过法院、案号和日期等线索，网站接入时不会直接把它们全部当成确认结果。程序只把能在原文头部逐字定位的法院和案号，放进有本地原文支持的字段；其他原始元数据另行保留。

案件叙述中的日期可能是签约日、事故日或开庭日，不能随便选一个当裁判日期。当前这套准入流程没有确认裁判日期时，就保持未知。

这里确认的是“当前保存的材料确实这样写”，并不等于已经去法院官网核验。后续阅读也要区分当事人主张、法院认定和作者评析。

### 4. 已有向量能否直接用

可以复用，但要先证明它与文字对应，而且生成方法与程序的查询方法一致。

案例准入会核对：每个向量对应的案件和片段编号、行号、1024 维格式、数值是否有效，以及是否按约定归一化。归一化是把向量调整到一致的长度尺度，便于比较相似程度。

网站接入时，当前案例包的 3,156 个向量全部保留，没有重新生成。这样既省去重复处理，也避免无理由改变原有检索输入。

上游早期脚本还生成过 384 维的字符哈希试验向量，用于没有正式模型时跑通流程。正式生成步骤已改用 BGE-M3 的 1024 维向量；网站当前使用的是这批正式结果。不能仅因为早期脚本也生成一个向量文件，就把它当作可直接发布的资料包。

### 5. 最后保存什么，程序如何使用

整理结果是一份数据快照。快照就是一组配套的数据文件，记录这次使用哪批案件、哪批片段和向量，避免运行过程中各自换成不同批次。

| 文件 | 给人理解的用途 |
|---|---|
| `cases.jsonl` | 案件全文和身份信息 |
| `chunks.jsonl` | 检索片段及其在全文中的位置 |
| `vectors.npy` | 与片段逐行对应的向量数字 |
| `manifest.json` | 文件清单、数量、生成约定和校验值 |

当前正式快照包含 825 份案件材料、3,156 个片段。发布脚本创建独立案例索引，检查导入结果，再切换 `maritime_cases_read` 读取入口。程序搜索后可以按同一快照和字符范围继续读全文。

**这一库可以用起来的依据：**找到的片段确实来自所标案件，前后文能接着读，引用中的身份信息有实际材料支持。

## 三、论文库：先读懂页面，再把摘录连回 PDF

论文经常有双栏、页眉、脚注、图表和参考文献。直接把 PDF 里的文字拼在一起，可能把左右两栏读串，也可能把页眉接进正文。因此，论文需要先恢复页面和段落结构，再生成检索卡片。

```text
原始 PDF（部分来自压缩包）
  → 官方 MinerU 提取文字与页面结构
  → 保留 Markdown、页面块与原 PDF 的对应关系
  → 整理正文，按段落和完整句子生成论文卡片
  → 记录章节、物理页码、文字位置及文件校验值
  → 生成或复用向量，形成标准资料包
  → 发布论文索引，接通卡片、引用和 PDF 阅读
```

### 1. 先保留 PDF，再用成熟工具提取内容

原始论文 PDF 保存在项目外的论文资源目录，部分文件有压缩包来源记录。项目使用官方 MinerU 4.2.1 做版面分析、文字识别和 Markdown 输出，没有另写一套 PDF 识别器。

提取后主要有两份材料：Markdown 便于阅读；`middle_json.json` 保存页面、文字块、块的位置和连续关系，便于知道一段话出现在 PDF 哪里。

已有完整解析结果、源文件也没有变化时，可以复用，不必每次重新识别。检查文件和页面结构完整后，还要抽样对照 PDF；这些结构检查本身不能保证扫描文字逐字准确。

### 2. 从页面结构整理正文，避免把不相关的文字混进来

卡片构建器读取 MinerU 的页面块，按结构整理正文，处理跨页段落，并依据标题编号恢复章节关系。页眉、页码、机构信息、脚注和参考文献等，会按结构与规则筛选，避免一律当作正文段落。

原 PDF 和 MinerU 原始输出继续保留。整理出的正文另存为 `body.txt`，论文卡片的字符位置以这份正文为准。

这是一个容易混淆的地方：同一段话在 PDF、Markdown 和整理正文里，排版和字符位置可能不同。所以，卡片必须写清楚“起止字符位置针对哪个文件”，不能拿正文的位置去截 Markdown。

### 3. 怎样把正文变成论文卡片

卡片主要保存论文原文摘录，不依靠聊天模型改写出一段摘要来替代原文。长段落按完整句子拆分；列举、条件和后果要尽量保持关联，章节路径也一起保留。

每张卡片回答几个具体问题：摘录是什么、来自哪篇论文、属于哪一节、在 PDF 第几页、对应哪些原始页面块、在整理正文的哪个范围。

题名和作者也有来源约束。作者优先取论文首页署名或该文自己的引文信息，文件名只作待核实线索；识别不出来就保留缺口。不能因为文件名末尾有几个字，就直接当成正式作者。

页码使用 PDF 从第一页开始数的物理页码。它可以让阅读器跳到对应页面，和期刊纸面上印的页码不一定相同，正式引注时需要区分。

引用时可以遵循一个简单原则：只有物理页码，就标明“PDF 第几页”；没有确认的纸面页码、年份或作者，不自行补齐。没有页码的材料，则用已有条号、案件编号、章节或正文位置帮助核查。这是整理引用时应遵循的规则，不表示网站已经自动生成了全部引注格式。

### 4. 把卡片和向量整理成配套文件

来源目录先保存论文卡片、论文登记表和校验结果；导入脚本再转换为程序使用的文件：

| 文件 | 给人理解的用途 |
|---|---|
| `cards.jsonl` | 可检索的摘录、检索文字和来源位置 |
| `sources.jsonl` | 有检索卡片的论文来源信息 |
| `papers.jsonl` | 全部论文目录，包括暂时没有有效卡片的论文 |
| `vectors.npy`、`vectors_meta.jsonl` | 向量及其与卡片编号、文字校验值的对应关系 |
| `manifest.json` | 文件清单、数量、模型约定和校验值 |
| `cards.offsets.json` | 每张卡在大文件里的位置，方便直接打开它 |

向量使用与法规、案例相同约定的 BGE-M3。生成约定相同、实际检索文字也相同时才复用已有向量；文字改变后，不能继续拿旧向量当新结果。PDF、Markdown、整理正文和页面结构分别计算校验值，核对时各自对应。

### 5. 从“卡片入库”走到“网页上真正能用”

当前论文物理索引是 `maritime_information_cards_v4`，读取入口是 `maritime_information_cards_read`。正式清单有 39,022 张卡片、1,145 篇目录论文，其中 1,144 篇有检索卡片；另 1 篇可以从目录查看原文，不算作已有可检索卡片。

网站使用时要把三个入口接在一起：搜索命中的卡片、回答里的论文引用，以及原 PDF 阅读。卡片编号找到论文登记信息，登记信息找到同一份 PDF，再用物理页码定位；打开时还核对文件校验值。

例如，用户搜索“货物损坏由谁承担”，命中一张论文卡片。卡片先让人读到相关摘录，再指出所属论文、章节和 PDF 页码；点开后，应看到同一篇论文的对应页面。需要核对前后文时，可以继续读正文或翻阅 PDF。搜索找到了相近内容，接下来仍要看作者讨论的条件是否与问题一致。

因此，搜索列表出现一张卡片还不算完成。需要从网页点进去看到正确 PDF，翻页、下载后仍是同一份文件，刷新历史回答后引用也能再次打开。已有浏览器验收覆盖了这些路径。

**这一库可以用起来的依据：**读者能从摘录走回同一篇论文的真实页面，知道这是谁的观点、发表于什么语境，而不会把学者建议当作现行法条。

## 四、统一流程：接收、整理、校验、检索和发布

三个库的原件不同，整理顺序却有共同原因：先认清资料，再整理文字；先保存来源位置，再切块；先核对数据与向量，再发布搜索入口。顺序颠倒时，搜索可能仍有结果，但结果无法可靠地回到原文。

### 1. 可以复用的八个步骤

下表是根据三库现有做法整理的通用流程。它是以后接入资料的工作规范；目前三库仍使用各自的脚本和字段，并没有合并成一个通用导入器。

| 步骤 | 做什么、为什么在这里做 | 交给下一步的结果 | 继续前怎样检查 |
|---|---|---|---|
| ① 接收并登记原件 | 保存源文件和来源信息，计算内容指纹，先确定“收到的是什么” | 原件、位置、文件清单和校验值 | 文件能打开；同名文件没有误覆盖；来源可追溯 |
| ② 解析成可读文字 | 按实际格式提取正文与结构，给后续整理提供文字依据 | 正文、页面或章节结构、解析记录 | 没有整页丢失、明显乱码或双栏读串；抽样与原件对照 |
| ③ 整理身份和元数据 | 确定每份资料是谁，保留日期、版本、作者或案件信息 | 稳定编号、资料登记记录 | 有依据才填写；未知项保留未知；同名不直接合并 |
| ④ 按语义切成片段 | 让搜索能找到具体内容，同时保留回到完整正文的位置 | 片段正文、顺序、所属完整资料的编号、原文位置 | 片段与对应正文切片一致；条件与结论不明显断开；保留范围符合约定 |
| ⑤ 生成或核对向量 | 为按意思找资料建立数字表示，必要时复用已有结果 | 向量、逐行对应表、生成约定 | 文字与向量一一对应；模型约定相同；变更文字不沿用旧向量 |
| ⑥ 形成完整资料包 | 把正文、片段、来源、向量和清单配齐，便于检查和重建 | 配套数据文件与总清单 | 编号、数量、路径、校验值互相对应；缺项明确报错 |
| ⑦ 导入并验证新索引 | 先建好待发布目录，读回检查后再更换网站入口 | 验证通过的搜索索引与切换记录 | 导入没有漏行或失败项；读回正文、数量和向量一致；失败时不切入口 |
| ⑧ 经过真实网页验收 | 从读者实际使用的入口检验搜索、阅读和引用 | 能实际使用的资料库与验收结果 | 搜得到、读得对、引用能打开、刷新后能找回；故障如实显示 |

例如，案例交付包已经有正文和向量，可以核对后从中间步骤接入；有完整 MinerU 结果的论文，也可以复用解析输出。仍然要核对配套关系，不能因为文件“以前处理过”就直接跳过检查。

### 2. 统一后，每份资料至少要能回答什么

统一流程时，可以约定共同需要的信息，不必强迫三个库采用完全相同的字段名。

| 共同问题 | 含义 | 各库保留的特点 |
|---|---|---|
| 这是什么资料 | 稳定身份、类型、标题和来源 | 法规有文献与条文两层；案例按案件；论文按原 PDF 与卡片 |
| 这一段从哪里来 | 所属完整资料、正文位置、必要的章节或页码 | 法规有条号与版本；案例有全文字符范围；论文有物理页和页面块 |
| 内容是否还是同一份 | 原件、正文、片段各自的校验依据 | PDF 哈希不能替代 Markdown 或正文哈希 |
| 搜索用了哪段文字 | 检索输入及它对应的向量 | 字段可以不同，但输入变了就要重新检查向量 |
| 程序正在读哪批资料 | 数据清单、索引和配套文件的对应关系 | 案例固定快照，法规与论文保留各自的资料及索引关系 |

这是一组共同问题，并不表示每库现有记录都叫 `source_id`、`snapshot_id` 或都有页码。没有实际页码的材料不能为了字段整齐而补一个数字。

### 3. 为什么原件、正文、片段和索引都要保留

可以用一次实际使用过程区分它们：用户提问后，索引先找出相关片段，程序再按片段记录找到正文。需要核对时，法规可以回看保存的来源文件，论文可以回看 PDF；案例的网站读取入口目前返回保存的案件全文，原 Word 另存于上游案例工作区。这不等于网页已经接通 Word 预览，也不能据此承诺回到最初采集的网站。

| 层次 | 主要职责 | 单独留下它会缺什么 |
|---|---|---|
| 原件 | 核对最初收到的内容、版式和出处 | 每次都从头翻找，难以批量检索 |
| 整理正文 | 提供连续可读、可核对的文字 | 可能丢失原始版式，需要原件对照 |
| 检索片段 | 让程序找到问题相关的具体部分 | 上下文有限，需要能接回全文 |
| 向量和索引 | 提高按字词或意思查找的效率 | 无法替代原文证据，也不能凭相似分数证明结论正确 |

源文件、处理脚本、生成约定和清单齐全时，索引损坏后有依据重建。只留一个能搜索的数据库，后续发现文字错了或引用接错，往往很难查清问题发生在哪一步。

### 4. 用五个黄金测试约束以后每批资料

先把成功条件写下来，再选解析工具、调整切块和发布数据。下面是可复用的验收要求，不表示本次写文档时重新跑过三库全量测试。

| 测试名称 | 测什么场景 | 防什么大坑 | 预期看到什么 |
|---|---|---|---|
| 原文没有接错 | 选一个片段，按记录位置读回正文；已保存来源文件的，再打开文件核对 | 张冠李戴、偏移基准用错、原件被替换 | 片段与保存的正文一致；能回到所标资料；有原件的，身份和定位也相符 |
| 重要信息没有丢 | 对照一份完整资料，检查正文、切分和排除项 | 法规缺例外、案件漏后半段、论文跨页断句 | 应保留内容可查；排除内容有理由；不会用片段冒充全文 |
| 身份和时间不乱填 | 检查历史法规、未知裁判日期、无作者或页码的材料 | 用错法律版本、把事故日当裁判日、编造作者和页码 | 有依据的信息可核对；没有依据的字段保持未知 |
| 向量与发布成套 | 故意让测试包的文字、行号或校验值不匹配 | 好文字配错向量，半批资料发布成正式结果 | 检查明确失败；待发布索引不替换正常入口 |
| 网页能真正使用 | 搜索、打开、引用，再刷新历史页面 | 后端有记录但前端打不开、刷新后链接失效 | 搜索、原文、引用指向同一资料；实际页面路径通过 |

具体抽样数量和整批检查范围应按资料规模确定。自动检查负责找字段、配对和文件错误；原件抽查负责发现识别或切分问题，专业阅读负责判断材料是否支持结论。

## 五、读完后，用五个问题检查是否讲清楚

读者不需要记住脚本名或数字。能用自己的话回答下面五问，才说明文档把主要逻辑讲清楚了；若读者说不清，应由文档补充解释或例子。

| 阅读测试 | 读者应当能说出的意思 | 回看位置 |
|---|---|---|
| 三个库分别从什么开始，到哪里结束 | 法规从多种原文件到可查条文；案例从 Word 正文与摘要，经交付包到可读快照；论文从 PDF 和页面解析到可回 PDF 的卡片。最后都经过网站使用入口 | 第一至三章 |
| 为什么不能收到文件就直接放进搜索库 | 要先确认身份、正文和位置，再核对片段与向量，否则可能搜得到却接错原文 | 各库的处理顺序、第四章第一节 |
| 为什么要留几种看起来重复的文件 | 原件供核对，正文供连续阅读，片段供定位，向量和索引供查找；它们职责不同 | 第四章第三节 |
| 找到结果后，怎样证明引用没有接错 | 按稳定编号、原文范围、章节或物理页回查，并核对相应文件；未知日期和页码不能补造 | 各库的来源检查、第四章黄金测试 |
| 以后换一批资料，能沿用什么 | 沿用八个步骤和检查要求；解析、身份字段和切分规则按资料类型选择。统一流程不代表已经有一个包办三库的程序 | 第四章第一、二节 |
